They reference a local image beside the document. The security gate blocks every
`file://` request except the document itself, so the image does not load and prints as
blank space. `tympan lint` reports it as `broken-asset` instead of letting it pass
silently; inlining local assets is the next fidelity item.

## What these numbers do not say

- **Fill is measured in the DOM, not from pixels.** It is the honest signal for "is this
  sheet half empty" (a painted background makes coverage metrics read 100%), but it is a
  measurement of the layout before printing, carried through the shrink actually applied —
  not a pixel-exact claim about the final sheet.
- **The corpus is generated, not scraped.** It is diverse by construction and reproducible
  byte for byte; it is not a sample of real customer documents, and no benchmark of 52
  synthetic sheets is.
- **Render time is one machine, warm browser, sequential.** It compares releases measured the
  same way; it is not a throughput claim (a cold start pays Chromium launch once).
- **Section layout only.** Flow layout does not exist yet; when it does, this file gets a
  second column and the delta between the two.

## Real deliverables: the layout-width fix, measured

The generated corpus above is synthetic. This section is the other half: three
real Kitch deliverables, converted before and after the 0.8.0 Phase 0 change
that capped the layout at the sheet's text column. Measured on the same machine,
same engine, same margins (A4 portrait, 0.4/0.5/0.4/0.5in → 698px column).

| document | layout before | pages | mean fill before | mean fill after | min fill before/after | page width scale before/after | bytes before/after |
|---|---|---|---|---|---|---|---|
| 01-brand-base.html | 774px | 11 → 11 | 35.2% | **39.6%** (+12.5% rel.) | 15.0% → 16.7% | 0.902 → **1.000** | 567,490 → 566,714 |
| 03-subscription-plans.html | 774px | 10 → 10 | 55.6% | **64.1%** (+15.3% rel.) | 15.0% → 16.7% | 0.902 → **1.000** | 426,415 → 424,050 |
| pot-counter.print.html | 774px | 4 → 4 | 26.8% | **31.9%** (+19.0% rel.) | 12.0% → 14.5% | 0.902 → **1.000** | 348,967 → 353,826 |

What the columns mean, and what they do not:

- **Page width scale 0.902 → 1.000** is the fix: every page used to be scaled to
  a 698px column because the layout was 774px. This is measured in the produced
  PDF, not inferred from the scale argument: the median glyph height on
  `03-subscription-plans` rose from **10.13pt to 11.24pt on every page that now
  prints at 1.0** (ratio 1.109, = 1/0.902). Page 6, which the narrower measure
  made taller than its sheet, lands at 10.05pt (0.894 × 11.24).
- **Page counts are identical** in all three documents. Nothing was reflowed
  onto extra sheets; the content that fit before still fits.
- **Byte deltas are small and structural**: the same pages, laid out at the
  authored scale. `pot-counter` grew 4.8KB because its text is now ~11% larger
  and so is its vector content, not because a page was added.
- **Two sections of `03` now shrink for height** (89% and 95%) where every page
  used to share one 90.2% scale. That is section layout doing its job under a
  narrower measure: those sections are taller than one page, and `--flow` is the
  fix for that, not this change. `tympan lint` reports it as `inconsistent-scale`
  — it did not say that before only because everything was uniformly scaled.
- **Fill is still far from full** (39–64%). The width fix recovers the 10% the
  scaling stole; it cannot fill a 1,045px sheet with a 400px section. That is
  the flow-layout work, and these numbers are its baseline.

Measured 2026-10-21, Windows 11, Node 24.18, Playwright 1.63.0 (pinned Chromium).

### The print-CSS claim, proved rather than asserted

`tympan lint` tells users tympan ignores a document's own print CSS. That was
false: the clean template copied the source's first `<style>` verbatim, so
`@media print` rules ran at print time. A fixture with
`@media print { .page-section { min-height: 2000px } }` failed with
`SPILL PAGES` on the pre-fix build even after six 10% shrink retries.

After stripping `@media print` and `@page` rules at the CSSOM, the same fixture
converts to 2 pages with per-page heights identical to an otherwise identical
control fixture (`test/layout-width.test.mjs`). `tympan lint`'s note about
source print CSS is now true, and a test keeps it true.

## Deck vs flow on the real Kitch deliverables: the layout-width fix's other half, measured

The Phase 0 table above is the width fix's baseline and its honest limit: fill
still lands at 39–64% because section layout cannot fill a 1,045px sheet with a
400px section. This is the A/B the flow layout was built against, same
fixtures, same engine, same margins, both fill readings taken from the produced
PDF (deck via the DOM-then-print verification, flow via the PDF text layer):

| document | mode | pages | mean fill | min fill | shrunk for height | bytes | wall |
|---|---|---|---|---|---|---|---|
| `01-brand-base.html` | deck | 11 | 0.396 | 0.167 | 1 (page 9 @ 0.664) | 564,371 | 7.1s |
| | **flow** | **6** | **0.810** | **0.098** | **none — scale 1.000** | **245,307** | **3.0s** |
| `03-subscription-plans.html` | deck | 10 | 0.641 | 0.167 | 2 (page 6 @ 0.894, page 8 @ 0.946) | 423,046 | 6.3s |
| | **flow** | **8** | **0.810** | **0.491** | **none — scale 1.000** | **132,203** | **2.2s** |
| `pot-counter.print.html` | deck | 4 | 0.319 | 0.145 | none (full-bleed deck) | 351,816 | 3.5s |
| | **flow** | **2** | **0.616** | **0.433** | **none — scale 1.000** | **238,229** | **2.5s** |

What the columns mean, and what they do not:

- **Flow does the filling the width fix could not**: mean fill rises 41%→80% on
  `01` and 64%→80% on `03`; `pot-counter` halves its sheets (4→2) while nearly
  doubling mean fill (31.9%→61.6%) and tripling its minimum (14.5%→43.3%).
- **Flow eliminates deck's height-bound fallbacks.** Deck's two shrinks on `01`
  (page 9 at 0.664) and two on `03` (0.894, 0.946) are the sections too tall for
  their sheet, rendered smaller than their neighbours. Flow prints every page at
  scale 1.000: no page of either variant carries a shrink, and verification
  reports zero clipped pages, zero blank pages, zero stranded headings, zero
  column overflow in every flow conversion of this table.
- **`pot-counter` deck stays as authored** — four pages, no shrink: its sections
  already fill their sheets at full width, so deck is the correct mode there
  (`--layout auto` picks it by the same measurement). The flow row is what
  `--flow` buys on prose, not an argument to flow a full-bleed deck.
- **`01`'s flow minimum is the honest wart**: one full-bleed band page lands at
  0.098 fill — two thousandths below the 10% flow floor the new lint rule flags
  (`tympan lint --layout flow` names it: `page 6 is 9% full (943px
  blank) — below the 10% flow floor`; the page fill is floor-rounded in this
  message so it can never print at the floor it was judged below). It is a
  break Chromium made for an unbreakable band, reported rather than hidden.
- **Fill floors, not margins**: these numbers are content extent per sheet, not
  visual ink — a painted background, footer margin boxes and page numbers are
  excluded by measurement design (the ink-coverage trap that started §“the
  generated corpus”, and why the prototype read a four-page document as zero
  waste).

Measured 2026-10-22, one pass, same machine/engine as the Phase 0 numbers
(Windows 11, Node 24.18, Playwright 1.63.0 pinned Chromium). §12 of
`PLAN-v0.8-pagination.md` recorded this same A/B a day earlier: page counts,
type conclusions and fill-to-fill ratios match; per-cell drift (fill ±0.01,
bytes within 1%) is run-to-run variance of the same measured pipeline, and the
comparisons here are all within this one pass. The shipped PDFs on disk differ
from the table's conversion-time sizes by the same sub-percent: metadata, not
layout — no page was added or removed.
